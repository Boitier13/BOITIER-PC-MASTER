# ADR EX1 — Cadrage de l'évolution de l'explorateur

**Date :** 19 novembre 2026
**Statut :** accepté pour EX1.0 et EX1.1 (EX1.2 → EX1.8 planifiés)
**Portée :** archivage des décisions de l'étude `ETUDE_EX1_EXPLORATEUR_2026-11-19.md`.
**Contrainte de méthode :** aucune reconstruction, aucun changement de technologie,
aucune suppression de fonctionnalité validée, réutilisation maximale de `fs_engine`.

---

## 1. Contexte

L'explorateur actuel charge un dossier entier (`directory_list`, plafond 5 000),
trie et filtre côté interface, et rend toutes les lignes dans le DOM. Au-delà de
quelques milliers d'entrées, l'écran devient lourd et la recherche récursive
reparcourt le disque à chaque requête.

Quatre arbitrages ont été rendus le 19 novembre 2026 :

| # | Décision | Incidence |
| --- | --- | --- |
| 1 | Périmètre **EX1 complet** (EX1.1 → EX1.7) | Les refactorisations sont pensées pour aller jusqu'aux colonnes configurables |
| 2 | **1 000 000 d'entrées**, **3 instantanés** | Plafonds, rétention et budget disque cadrés (≈ 1,3 Go) |
| 3 | **Aperçu texte ≤ 64 Ko**, désactivé par défaut, lot distinct (EX1.8) | Seule capacité de lecture de contenu, isolée et bornée |
| 4 | **Ouverture Windows hors EX1** (pré-étude EX2.0) | `std::process` reste interdit dans le code livré |

---

## 2. Décisions d'architecture

### D1 — La pagination appartient au moteur, pas à l'interface

Le tri précède la découpe : la page `n` est déterministe et deux pages successives
ne peuvent ni se recouvrir ni sauter une entrée. C'est la seule façon d'obtenir un
défilement correct sans charger tout le dossier.

### D2 — Aucune nouvelle commande pour la pagination

`directory_list` est étendu, pas doublé : un seul chemin IPC, un seul contrat,
donc aucune divergence entre le mode réel et le mode démonstration.

### D3 — Les champs ajoutés sont optionnels ou à valeur par défaut

`ListOptions` accepte `offset`/`limit` avec des valeurs par défaut (0 et « tout ce
qui est retenu »). Un appelant qui ignore la pagination obtient exactement le
résultat d'avant : les tests existants et les autres écrans ne changent pas.

### D4 — Le niveau de sécurité reste `maxEntries`

`limit` est borné par `max_entries` dans le moteur. Aucune requête ne peut
demander davantage que le plafond de sécurité, même si l'interface est
compromise.

### D5 — Le fenêtrage de liste est un repli silencieux

Si la hauteur du conteneur n'est pas mesurable (rendu sans moteur de mise en
page, environnement de test), le fenêtrage se **désactive** et toutes les lignes
sont rendues. Le rendu et les tests restent identiques à l'existant.

### D6 — Les colonnes quittent le rendu

`EXPLORER_COLUMNS` devient la source unique (ordre, libellé, clé de tri). La
personnalisation (EX1.7) filtrera cette liste sans toucher au tableau.

### D7 — L'index SQLite n'est pas activé en EX1.1

`db_status` reste honnête (« non ouvert »). La base n'est ouverte qu'en EX1.2,
avec `rusqlite` (`bundled`) et un runner de migrations.

### D8 — Un seul canal de progression

L'indexation et la mesure réutilisent `scan://progress` et `walk_cancel`. Aucun
second mécanisme d'annulation n'est introduit.

### D9 — Les contrôles structurels accompagnent chaque incrément

Chaque garde-fou ajouté ici est vérifié par `scripts/check-foundation.mjs` :
pagination bornée, absence de `std::process`, absence de SQL destructive,
parité démonstration/réel.

## 4. Contrat de pagination (EX1.1)

### 4.1 Rust — `fs_engine/listing.rs`

```rust
pub struct ListOptions {
    pub include_hidden: bool,
    pub include_system: bool,
    pub directories_first: bool,
    pub max_entries: usize,   // plafond de sécurité, borne aussi `limit`
    pub offset: usize,        // défaut 0
    pub limit: Option<usize>, // défaut None = tout ce qui est retenu
}

pub struct DirectoryListingDto {
    pub path: String,
    pub parent: Option<String>,
    pub entries: Vec<FileEntryDto>,
    pub total: usize,      // entrées présentes avant filtres et plafond
    pub truncated: bool,   // plafond atteint
    pub denied: usize,
    pub is_protected: bool,
    pub matched: usize,    // retenues après filtres et plafond
    pub offset: usize,     // décalage effectif
    pub returned: usize,   // taille de la page
    pub has_more: bool,    // reste-t-il des entrées ?
}
```

Ordre garanti : dossiers d'abord (si demandé), puis nom (`compare_key`, insensible
à la casse et numérique). `offset > matched` renvoie une page vide avec
`has_more: false` ; `limit: 0` renvoie une page vide avec `has_more` exact.

### 4.2 TypeScript

`ListOptions` gagne `offset?` et `limit?` ; `DirectoryListing` gagne `matched?`,
`offset?`, `returned?`, `hasMore?`. Les champs restent **optionnels** pour que les
doubles de test et les autres écrans restent valides.

### 4.3 Interface

`use-paged-listing.ts` : `PAGE_SIZE = 1 000`, `MAX_PAGES = 20`. Les pages sont
enchaînées tant que `hasMore` est vrai, avec un garde-fou de 20 pages (20 000
entrées). Si `hasMore` est absent (service antérieur), une seule page est
demandée : comportement historique conservé.

## 5. Schéma SQLite v2 (figé, exécuté en EX1.2)

```sql
-- 002_index.sql — NON EXÉCUTÉ tant que le runner de migrations (EX1.2) n'existe pas.

ALTER TABLE entries ADD COLUMN category        TEXT;
ALTER TABLE entries ADD COLUMN created_at      TEXT;
ALTER TABLE entries ADD COLUMN accessed_at     TEXT;
ALTER TABLE entries ADD COLUMN is_symlink      INTEGER NOT NULL DEFAULT 0;
ALTER TABLE entries ADD COLUMN is_protected    INTEGER NOT NULL DEFAULT 0;
ALTER TABLE entries ADD COLUMN access_denied   INTEGER NOT NULL DEFAULT 0;
ALTER TABLE entries ADD COLUMN attributes_raw  INTEGER;
ALTER TABLE entries ADD COLUMN link_target     TEXT;
ALTER TABLE entries ADD COLUMN file_id         INTEGER;
ALTER TABLE entries ADD COLUMN dir_size_bytes  INTEGER;
ALTER TABLE entries ADD COLUMN owner           TEXT;

CREATE INDEX idx_entries_snapshot_type  ON entries (snapshot_id, category);
CREATE INDEX idx_entries_snapshot_mtime ON entries (snapshot_id, modified_at);

CREATE VIRTUAL TABLE entries_fts USING fts5(
    name, path,
    content='entries', content_rowid='id',
    tokenize="unicode61 remove_diacritics 2",
    prefix='2 3 4'
);

CREATE TABLE index_jobs (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    snapshot_id INTEGER NOT NULL REFERENCES snapshots(id) ON DELETE CASCADE,
    scan_id     TEXT NOT NULL,
    status      TEXT NOT NULL,
    visited     INTEGER NOT NULL DEFAULT 0,
    denied      INTEGER NOT NULL DEFAULT 0,
    truncated   INTEGER NOT NULL DEFAULT 0,
    started_at  TEXT NOT NULL DEFAULT (datetime('now')),
    finished_at TEXT
);
```

Règles : migration transactionnelle, `schema_version` incrémenté après succès,
`PRAGMA integrity_check` au démarrage, aucune table utilisateur modifiée, et
`entries_fts` en mode `content=` (pas de duplication de texte).

## 6. Conséquences

- **Comportement visible** : identique pour un dossier de moins de 1 000 entrées ;
  au-delà, l'affichage se remplit par pages et le défilement reste fluide.
- **Performance** : une réponse IPC ne dépasse plus 1 000 entrées ; le DOM ne
  contient que la fenêtre visible (≈ 40 lignes) au-delà de 200 entrées.
- **Tests** : 5 tests Vitest ajoutés (pagination, repli, borne de pages, écran,
  erreur de moteur) et 3 tests Rust ajoutés dans `listing.rs`.
- **Contrôles** : 12 contrôles « Explorateur EX1 » ajoutés à
  `scripts/check-foundation.mjs`.
- **Ce qui ne change pas** : contrat `SystemService` (aucune méthode retirée),
  commandes existantes, mode démonstration, lecture seule, typographie validée.

## 7. Suites

EX1.2 (index SQLite, `rusqlite`, migrations, ingestion via `traverse`) démarre sur
ce socle : la pagination est déjà côté moteur, l'interface est déjà capable de
consommer des pages, et le schéma v2 est figé ici.
